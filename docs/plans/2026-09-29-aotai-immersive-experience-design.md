# 鳌太线沉浸式徒步体验项目：整体设计方案

- 文档日期：2026-09-29
- 文档版本：v0.4
- 项目目录：`D:\Projects-X\AoTai-Route`
- 文档性质：整体设计基线，不是逐项编码实施计划。
- 当前状态：阶段 1 已获得用户反馈；阶段 1.1 已补充鸟瞰自动漫游与同步小地图，待再次体验。真实场景与素材未落实；依赖版本及当次性能数据见各阶段验收记录。

## 1. 项目定位

构建一个运行在普通电脑浏览器中的鳌太虚拟旅程体验。保留第一人称徒步，并按首轮反馈增加离地约 30 米的自动鸟瞰模式和小地图。最终目标包括亲自行走、驻足听风、观察远山、云雾与光线变化；声音和动态天气目前尚未实现。

核心目标是沉浸看景，不是生存闯关。用户可选择身在山中的徒步或自动鸟瞰；后者仍是可转头、变速、暂停的实时三维体验，不是航拍视频。

**制作策略：真实地形打底，重点近景精细制作，沿旅程分段加载。先完成一段值得反复体验的旅程，再扩展全线。**

### 1.1 已确认的用户需求

| 项目 | 已确认内容 |
| --- | --- |
| 用户背景 | 徒步爱好者，希望获得尽量真实的虚拟穿越体验 |
| 体验取向 | 风景沉浸：重点看景、听风和体验旅程，弱化体力与生存压力 |
| 目标设备 | 普通电脑 |
| 技术意向 | Three.js 及相关技术栈 |
| 当前工作范围 | 已获阶段 1 开发授权；阶段 2—5 暂不开始 |

### 1.2 暂定设计前提

- 优先桌面浏览器、键鼠操作、单人体验，耳机为推荐而非必需设备。
- 不以独立显卡为前提；具体兼容范围需要在选定测试机上验证。
- 第一版以 Windows 上的 Chrome／Edge 为主要验证对象，其他浏览器后续补充测试。
- 不要求用户登录；存档与设置优先保存在本机浏览器。
- 技术选型为推荐方案，安装前核对稳定版本与依赖兼容性，不默认采用预览版本。

### 1.3 现实边界与真实性声明

鳌太现实穿越存在明确禁令及安全限制。项目定位为数字体验，不作为现实通行许可、导航工具或安全能力认证，不为制作素材而组织违规实地采集。[西安市秦岭生态环境保护管理局相关说明](https://xaqlbhj.xa.gov.cn/xwdt/qldt/2010522311248584706.html)、[国家体育总局 2026 年 1 月通知](https://www.sport.gov.cn/dszx/n5414/c29349451/content.html)

在作品说明中区分：有数据依据的地形、有资料依据的视觉还原、艺术化重建的近景，以及经过编排的天气和旅程。不能把程序生成细节宣传为逐石实测复刻。

## 2. 体验设计

### 2.1 三种主要体验状态

1. **自由徒步**：用户控制方向与速度，可以停下、回头、观察近景与远景。
2. **自动漫步**：沿经过验证的虚拟体验路径缓慢前进；视线仍由用户控制，可随时接管移动。
3. **驻足观景**：暂停移动或隐藏界面，观察环境并聆听声音；不是用全屏菜单替代山景。

后续通过章节组织较长旅程，允许继续上次体验或直接进入开放章节。自由徒步是在已制作和验证的区域内自由移动，不承诺第一版覆盖任意方向的无限开放世界。

### 2.2 主要体验流程

```text
进入项目
  → 简短作品说明、设备检测与音频启用
  → 开始样段／继续上次体验
  → 按需显示简短操作提示
  → 自由徒步 ↔ 自动漫步 ↔ 驻足观景
  → 暂停、调整设置、保存退出
```

后续加入章节选择，不让首页成为功能繁杂的游戏大厅。进入三维场景后，界面应尽量少遮挡景色。

### 2.3 真实感的优先顺序

| 维度 | 设计要求 |
| --- | --- |
| 山体尺度 | 保持可信高差、坡度、山脊轮廓和远近关系，避免微缩模型观感 |
| 行走体感 | 合理人眼高度、接地运动、坡度影响步速、可靠碰撞，避免漂浮摄像机 |
| 脚下近景 | 岩块、碎石、草甸、泥土及交界过渡，而不是只铺卫星影像 |
| 环境声音 | 风声变化、不同材质脚步、轻微衣物摩擦与环境开阔度差异 |
| 光照天气 | 自然曝光、远山空气透视、云影、柔和雾层与连续过渡 |
| 旅程节奏 | 有开阔与遮蔽、行进与停留的变化，允许安静和重复的路段 |

总体优先级：**稳定流畅与舒适操作 → 地形尺度与行走 → 声音与自然光 → 近景细节 → 附加特效。**

### 2.4 克制的身体反馈

- 上坡可略微减速，增加轻微呼吸与衣物声音，但不设置阻断看景的体力耗尽机制。
- 不设置饥饿倒计时、死亡惩罚、强制补给、强制收集任务。
- 大幅镜头晃动、动态模糊不作为默认表现方式。
- 镜头晃动可关闭，视野角度、鼠标灵敏度和各类音量可调整。
- 支持自动漫步、暂停及清晰的键盘焦点，降低持续操作负担。

## 3. 场景构建方案

### 3.1 备选方案比较

| 方案 | 优点 | 局限 | 结论 |
| --- | --- | --- | --- |
| 真实地形＋精细体验区域 | 兼顾地理辨识度、自由移动与近景品质 | 仍需制作和校验场景资产 | 推荐 |
| 全景照片／视频串联 | 有合适授权素材时可获得摄影级观感 | 移动视差、视角和交互受限 | 可作资料或辅助展示，不作主体验 |
| 全区域统一高精度重建 | 覆盖完整、自由度高 | 数据、制作量、下载与运行成本高 | 不作为首版目标 |

### 3.2 地形与资产的三层结构

**第一层：真实地形骨架。**

寻找合法可用的数字高程数据，构建山体、山脊和远景。候选包括 Copernicus GLO-30，其全球数据约为 30 米分辨率，并有来源标注要求。该数据属于地表模型，处理时需关注植被等地表覆盖影响，不能直接当作精细裸地与步道模型。[Copernicus 数据说明](https://dataspace.copernicus.eu/explore-data/data-collections/copernicus-contributing-missions/collections-description/COP-DEM)

30 米级数据无法还原脚下石块、小沟或具体落脚位置；加密网格和插值不等于增加真实测量信息。采用前还需要实际检查目标区域覆盖、质量与使用条件，目前尚未下载或验证具体数据。

**第二层：参考资料还原。**

通过有授权的照片、视频和可靠地理资料，确认典型岩石、植被、地貌与重要视线轮廓。资料不足处标记为艺术化重建。照片、视频可供参考不等于其资产可直接复制进作品，授权应分别核对。

**第三层：可行走区域精修。**

将制作预算集中在玩家能够接近、停留和观察的区域。远山低细节、近处高细节；美术模型与碰撞模型分离，避免把所有视觉细节都转为高成本物理几何。

### 3.3 数据与资产处理流程

```text
来源与授权登记
  → 下载／收集允许使用的高程及参考资料
  → 检查覆盖、缺失值、坐标系与高程基准
  → 统一地理坐标，转换为适合运行时的局部米制坐标
  → 裁切地形、生成分块和多级细节
  → 制作材质、近景模型与简化碰撞体
  → 校验区块边界、坡度与可行走性
  → 压缩并生成带版本的章节资源清单
  → 浏览器加载与实机验收
```

- 不混用未经转换的地理坐标与网络地图偏移坐标。
- 同一地形源派生渲染地形与碰撞地形，并检查两者的一致性。
- 大范围旅程按章节局部坐标组织；是否需要浮动原点由实际范围决定，不预先增加复杂度。
- 为数据、模型、纹理和音频保存来源、作者、许可、署名要求与修改记录。
- 不通过缩小整座山缩短游玩时间，使用章节切换、可选跳过和自动漫步控制节奏。

## 4. 视觉与声音方向

### 4.1 视觉基调

偏自然纪录片：真实曝光、克制调色、可信材质粗糙度、远山的空间层次。避免过量泛光、过饱和色彩、始终清晰的超远景与强制电影式景深。

首版先精调一种基础光照和晴朗到薄雾的柔和过渡。完整昼夜、四季、暴风雪和高级湿润效果属于后续候选，不挤占样段预算。

### 4.2 普通电脑的表现策略

- 太阳光与环境光为主，动态阴影集中在必要的近景范围。
- 云优先采用分层贴片等低成本方式；雾优先采用距离与高度相关的近似表现，暂不依赖昂贵体积效果。
- 重复岩石和植被共享几何与材质，采用批量绘制或实例化。
- 地表通过合适的材质混合减少明显重复，避免用单一大贴图承担全部细节。
- 云影、雾、植被摆动和风声尽量由同一环境状态驱动，避免听感与画面互相矛盾。

### 4.3 声音设计

- 风声分为持续底层与缓慢变化的局部层，不使用明显重复的短循环。
- 石面、碎石、草地等脚步声随真实落步节奏触发，停下后停止。
- 呼吸和衣物声保持克制，提供独立音量或关闭选项。
- 有合适资料和预算时再增加经核实的当地自然声，避免随意堆叠鸟鸣。
- 空间音频帮助表现方向与距离；复杂遮挡先用可控近似实现。
- 音频由用户操作后启用；不可播放时清楚提示，不阻断无声体验。

## 5. 功能范围与优先级

### 5.1 首个可玩版本必须包含

- 10—15 分钟连续体验样段，包含近景岩石、开阔山脊与远山观景位置。
- 实际选址、连接关系和长度由资料校验与正常步速测试确定，不在此文档中虚构实地路线顺序。
- 第一人称移动、碰撞、斜坡与小障碍处理。
- 可随时接管的自动漫步。
- 完整的基础材质、自然光照和一种轻量天气过渡。
- 风声、地面差异脚步及轻微身体声音。
- 暂停、隐藏界面、画质与舒适性设置。
- 断点继续、资源加载反馈与失败重试。

### 5.2 样段验收后扩展

- 增加有差异的章节，逐步连接更长旅程。
- 晨昏或更多经过美术调校的天气预设。
- 可选摄影模式与旅程回顾。
- 更多经资料支持的地貌、植被与音景。

### 5.3 首版不做

- 多人联机、账号、排行榜和复杂业务后台。
- 硬核生存、复杂背包、装备制作与死亡惩罚。
- 全线逐石扫描级复刻或无限开放世界。
- 完整四季及所有极端天气。
- 手机和 VR 与桌面版同步适配。
- 现实路线导航、实时气象安全判断或专业户外训练认证。

## 6. 技术架构

### 6.1 推荐技术栈

| 模块 | 推荐方案 | 作用与约束 |
| --- | --- | --- |
| 工程基础 | TypeScript＋Vite | 类型约束、开发预览、静态构建 |
| UI 与场景组织 | React＋React Three Fiber，按需使用 Drei | 组件化场景与少量界面；不为方便而引入大量未用组件 |
| 三维渲染 | Three.js，首版 WebGL2 | 优先验证兼容性与既定视觉目标 |
| 行走和碰撞 | Rapier | 使用角色控制器作为基础，另行调校山地移动 |
| 应用状态 | Zustand | 章节、设置和低频界面状态，不承担所有逐帧数据 |
| 音频 | Web Audio API／Three.js 音频能力 | 空间声与混音，避免重复建立两套音频系统 |
| 本地存档 | IndexedDB | 保存位置、章节和设置，包含版本号与校验 |
| 资产制作 | Blender | 岩石、植被、碰撞体和资产优化 |
| 地形预处理 | QGIS／GDAL | 高程检查、坐标转换、裁切与派生数据 |
| 资源交付 | GLB、压缩纹理、分块与多级细节 | 实测后确定纹理与几何压缩组合 |
| 验证 | 单元测试、浏览器流程测试、截图与性能分析 | 算法正确性、交互可用性与视觉验收分开进行 |

R3F 负责场景组织，运动和动画在逐帧循环更新，不通过 React 状态每帧重绘界面；复用对象与资源，减少频繁创建、销毁带来的开销。[R3F 性能指南](https://r3f.docs.pmnd.rs/advanced/pitfalls)

Rapier 的角色控制器提供碰撞、斜坡和小障碍处理基础，但不等于自动获得真实徒步手感，仍需专项调校与回归测试。[Rapier 角色控制器文档](https://rapier.rs/docs/user_guides/javascript/character_controller/)

WebGPU 作为后续独立技术评估，不视为一键升级。其材质与后处理路径存在差异，首版不混用两套不兼容的渲染方案。[Three.js 渲染器说明](https://threejs.org/manual/pages/webgpurenderer)

### 6.2 高层结构

```text
高程、参考资料、授权资产
           │
           ▼
离线资产处理与验证
           │
           ▼
带版本的章节资源包
           │
           ▼
浏览器运行时
├─ 场景管理：章节、资源加载、区块生命周期
├─ 地形渲染：远近细节、材质、植被与岩石
├─ 玩家系统：输入、行走、碰撞、相机、自动漫步
├─ 环境系统：光照、云雾、风与天气过渡
├─ 音频系统：空间音景、脚步与混音
└─ 应用层：菜单、设置、存档、提示与错误恢复
```

第一版采用单个前端应用与离线资产处理流程，不引入微服务、在线用户数据库或服务器实时模拟。需要分享时可评估静态托管，但当前不上传外网。

### 6.3 运行与数据流原则

- 输入进入玩家系统，运动通过碰撞求解后更新相机；自动漫步也必须经过同一安全运动路径，不能绕过碰撞直接移动相机。
- 物理使用固定步长或受控时间步，画面独立插值；限制异常长帧，失去焦点后避免回到页面时大幅跳动。
- 环境状态统一驱动云雾、光照与相关音频变化。
- 章节采用数据配置，描述出生位置、体验路径、资源清单、环境预设和检查点，不把所有内容硬编码进场景组件。
- 保存用户位置时同时记录章节及内容版本，恢复前验证位置仍处于有效区域。
- 尚未完成加载的区块不得成为可进入区域；加载顺序同时考虑视觉资源与碰撞资源。

## 7. 关键架构决策记录（ADR 摘要）

以下均为当前推荐设计，具体实现选择需在原型验证后确认。

| 编号 | 决策 | 理由 | 代价与重新评估条件 |
| --- | --- | --- | --- |
| ADR-001 | 采用真实地形与精修区域的混合重建 | 兼顾辨识度、自由行走和制作成本 | 近景不是逐石测绘；若获得合法高精度资料再提升 |
| ADR-002 | 普通电脑桌面浏览器优先 | 对齐用户设备和进入体验的便利性 | 限制高级特效；硬件基线明确后再确定上限 |
| ADR-003 | 首版采用 WebGL2 | 收敛兼容性与材质、后处理验证范围 | WebGPU 新能力暂不使用，未来迁移另行评估 |
| ADR-004 | R3F 管理组件，实时运动与低频 UI 状态分离 | 兼顾可维护性与逐帧更新效率 | 需要明确状态所有权，避免重复驱动同一对象 |
| ADR-005 | 使用 Rapier 角色控制器，简化碰撞体 | 降低基础碰撞开发风险 | 手感仍需调校，复杂岩石区域需专项测试 |
| ADR-006 | 单机优先、本地存档、无业务后端 | 首版需求不需要在线服务 | 不提供跨设备同步，清理浏览器数据可能丢失存档 |
| ADR-007 | 先样段再扩展，使用章节和分块加载 | 先验证质量与成本，不一次加载全线 | 需要处理边界、资源预取与章节衔接 |
| ADR-008 | 风景沉浸而非生存压力 | 对齐用户明确选择 | 身体与天气反馈不构成严格生理或气象模拟 |

## 8. 性能、兼容性与可靠性

### 8.1 性能目标

- 在选定的普通电脑测试机上争取稳定 30 FPS；性能充足时开放 60 FPS。
- 以 1080p 显示环境为参考，UI 保持清晰，三维内部渲染分辨率允许动态降低。
- 最低配置、具体显存／内存预算、首次进入时间与资源包体积暂未定案，须由硬件基线和样段实测确定。
- 不把上述目标理解为所有普通电脑上的性能保证。

### 8.2 性能措施

- 近处精细、远处简化，提前加载行进方向资源，及时卸载不需要的区块。
- 共用材质与几何，重复物件采用实例化，减少绘制调用。
- 控制纹理分辨率、阴影距离和透明叠加；资源压缩与解码成本一并评估。
- 动态分辨率和画质降级采用平滑策略，避免频繁跳变。
- 默认关闭动态模糊和重景深，必要时关闭高成本后处理。
- 持续记录帧耗时、卡顿、内存增长、绘制量、资源体积和加载耗时，而不是只看平均 FPS。

### 8.3 失败模式与处理

| 风险或故障 | 处理原则 |
| --- | --- |
| 浏览器或设备不支持所需渲染能力 | 展示明确兼容提示，不停留在黑屏 |
| GPU 上下文丢失 | 暂停体验，尝试重建；无法恢复时引导从检查点重新进入 |
| 章节资源加载失败 | 显示失败状态与重试；保留已加载场景，不让角色进入缺失区域 |
| 帧率持续不足 | 降低内部分辨率、阴影与特效，允许用户手动选择档位 |
| 角色卡住或掉出地形 | 提供回到最近有效检查点的恢复方式，并记录用于修复的位置 |
| 存档损坏或版本不匹配 | 保留可恢复设置，说明情况后回到有效章节检查点 |
| 浏览器存储不可用 | 提示本次不能保存，但仍允许继续体验 |
| 音频或指针锁定未启用 | 通过明确按钮请求启用；退出锁定后暂停移动，避免误操作 |

### 8.4 隐私与资源安全

- 首版不采集用户真实定位，不要求账号，不默认上传存档或行为数据。
- 资源来源和授权可追溯；不把私有访问凭据放入前端构建产物。
- 对资源清单、章节配置和存档做基本格式及边界校验。
- 发布时再依据实际托管方式配置 HTTPS、资源访问与内容安全策略，不为解决兼容性关闭浏览器安全机制。

## 9. 开发里程碑

开发按 5 个可体验阶段推进。每阶段交付可在本地浏览器运行的版本、真实截图、验收记录与已知问题；用户体验并确认方向后再进入下一阶段。详细交付清单见[阶段开发路线图](2026-09-29-aotai-development-roadmap.md)。

资料收集、授权登记与硬件基线建立是阶段 1 的前置工作，不单独安排一个长期只有文档、没有体验的阶段。性能、舒适性与兼容性在各阶段持续验证，不拖到最后集中处理。

### 阶段 1：可行走原型——先走起来

交付 v0.1：一个可步行探索的简化山地场景，包含第一人称移动、碰撞、坡面处理、暂停、可关闭的镜头晃动和基础性能检测。通过本地 HTTP 地址直接体验。

验收：在约定测试机上走、停、转向和上下坡自然，不明显穿地、漂浮或频繁卡住；记录初始性能。若暂用测试地形，清楚标为技术验证场景，不能当作鳌太还原。

### 阶段 2：地形与画面样段——让山具有辨识度

交付 v0.2：依据已核实地形与参考资料制作的短样段，包含山体轮廓、近景岩石、草地或草甸、远山层次、自然光照和一个重点观景位置；附来源与艺术化重建说明。

验收：有可信尺度和地貌辨识度，不只是任意程序山；实际画面与参考进行对照，且相较原型没有不可接受的性能退化。

### 阶段 3：声音与天气——形成临场感

交付 v0.3：在画面样段上加入风声、不同地面脚步、轻微衣物声、云影、晴朗到薄雾的过渡、自动漫步、隐藏界面和独立音量控制。

验收：戴耳机或使用扬声器时都有清楚的听感变化；停步、换地面与天气变化相互协调；自动漫步可随时接管，移动仍经过碰撞求解。

### 阶段 4：完整精品样段——形成可独立交付的 MVP

交付 v0.4：10—15 分钟连续体验，补齐开始／继续、简短操作提示、设置、断点存档、加载反馈、错误恢复、画质档位、说明和署名。

验收：用户能独立完成进入、体验、保存退出和恢复；正常步速下时长合理；约定普通电脑上争取稳定 30 FPS，有实际测试记录；这是首个完整可用版本，不必等待全线扩展。

### 阶段 5：章节化旅程——从一段走向多段

交付 v0.5 起：按小批次增加有差异的章节、章节选择、进度保存、分块预取与资源卸载；可选晨昏或摄影功能另行排序。每增加一个章节即形成一个可验收版本。

验收：新增内容不是重复山坡，切换与存档稳定，长时间运行无持续异常内存增长。完整区域、章节数量和发布时间根据资料与单位制作成本另行确认，不把“进入阶段 5”等同于“完成全线”。

当前没有确定团队规模、资产预算和工期。阶段 1 建立技术与硬件基线，阶段 2 记录资产制作成本，随后再估算阶段 3—5 的工作量与排期。

## 10. 验证与验收方法

### 10.1 自动化与功能测试

- 坐标转换、尺度、高程采样、资源配置和存档迁移采用可复现测试。
- 测试平地、连续坡面、小障碍、边缘、区块接缝和不同帧率下的移动。
- 覆盖开始、暂停、自动漫步接管、设置、保存退出与继续体验。
- 验证加载失败、音频未启用、存储异常和 GPU 恢复等错误路径。
- 自动化检查不能替代真实用户的行走手感、听感和眩晕反馈。

### 10.2 本地浏览器验证约定

- 优先发现已配置的 `chrome-devtools` 工具并调用 `list_pages`，然后新建本任务页面；使用唯一 `isolatedContext`，所有操作使用本次返回且确认归属的 `pageId`。
- 使用项目本地 HTTP 开发预览，监听 `127.0.0.1`，不默认使用 `file://` 或监听 `0.0.0.0`。
- 确认真实端口与页面加载结果，不沿用旧会话临时端口；不对外服务用户主目录或无关文件。
- 同时使用页面快照与实际截图检查结构、渲染与视觉；只有验证后才报告“已看到页面”。
- 只清理本任务创建的页面与进程，不终止其他任务浏览器或删除共享配置。
- 区分工具是否连接、地址是否可访问和页面是否成功渲染，不把某个通道失败等同于所有浏览器都不可用。
- 性能最终应在用户实际体验设备和正常浏览器环境中确认；无头环境的性能数据不能直接代替实际设备体验。

### 10.3 总体验收标准

> 在约定的普通电脑上，用户能否舒服地走上十几分钟，并愿意停下来看看山。

具体检查：

- 能辨认场景的地理与地貌特征，而不只是泛化的程序生成山地。
- 行走接地、坡度合理、自动漫步随时可接管。
- 画面稳定，云雾和细节切换没有明显破坏沉浸感的跳变。
- 停步、换地面、进入遮挡环境时，声音变化可信。
- 舒适性设置有效，无强制强晃动或动态模糊。
- 能可靠保存和恢复旅程；异常时可恢复，不丢失全部进度。

## 11. 待验证事项与主要风险

| 事项 | 当前状态 | 下一步 |
| --- | --- | --- |
| 实际设备 CPU、GPU、内存与浏览器 | 未核实 | 经用户同意后以实际设备建立性能基线 |
| 首段具体区域及真实连接关系 | 未确定 | 结合资料质量、代表性和制作成本选择 |
| 目标区域高程数据质量 | 尚未下载验证 | 检查覆盖、缺失值、地表偏差及轮廓 |

| 长旅程内容重复与制作量 | 内容风险 | 先验证样段质量和单位制作成本，再扩展 |
| 完整旅程范围、预算与工期 | 未确定 | 在首段验证后评估，不提前承诺 |

## 12. 当前结论与后续工作边界

1. 产品方向已收敛为普通电脑上的风景沉浸式第一人称虚拟徒步。
2. 推荐以 Three.js 为核心，采用真实地形与精修近景结合的制作方式。
3. 先完成可行走原型，再打磨 10—15 分钟精品样段，通过后扩展章节。
4. 画质服从稳定性与舒适性，不通过大量高成本特效替代真实尺度、声音和资产质量。
5. 阶段 1 已有可行走程序测试地形、操作界面、设置、18 项测试与生产构建；未下载真实场景资产，具体边界和工具限制见[阶段 1 验收记录](../reviews/phase-01.md)。
6. 下一步是用户体验并验收阶段 1；不一次性铺开全部阶段，也不将技术原型称为完整真实鳌太体验。
